# Проверка безопасности и корректности — 26 октября 2026

Проверены фактические исходники мобильного клиента и FastAPI, а не только отчёты исполнителей. Проверка охватывает локальное демо и серверный симулятор. Это не аппаратный аудит и не подтверждение работы Android APK. Рецензент ранее реализовал мобильную доменную модель; проверка её логики не является независимым аудитом третьей стороной.

## Обнаруженные проблемы

### P1 — Исправлено: неоднозначная команда оставалась незавершённой после противоречащей цели телеметрии

Место: `backend/specwatt_api/app.py`, функции `command_rejection` и `telemetry`; клиент `mobile/specwatt-app/src/screens/server.tsx`, `unresolved`/`waiting`.

В исходной проверенной версии команду CH1 off можно перевести в `timeout`, затем отправить полный образец симулятора `{CH1:1.8,CH2:0,CH3:2.4}`. Образец делает контроллер свежим и очищает `uncertain`, но команда остаётся `timeout`, поскольку подтверждённое состояние не совпало с целью. Клиент навсегда блокирует следующие команды, а API принимает новую команду с новым ключом: проверка in-flight учитывает только `requested` и `sent`.

Подтверждено отдельным запуском FastAPI TestClient с временной SQLite:

```text
after_sample_freshness: fresh
old_command_status: timeout
new_command_http: 200
new_command_status: requested
```

Исправление перепроверено: полная достоверная телеметрия завершает сверку и при несовпадении с целью. Статус становится `reconciled`, причина — `target_not_reached`. Тот же ключ возвращает ту же завершённую команду; повторного выполнения нет. Ручной приоритет сохраняется от исходного времени команды. Клиент переводит статус нейтрально как «Сверена с телеметрией», а причину — «целевое состояние не достигнуто», не изображая успешное выполнение.

Повторный независимый запуск того же сценария после исправления:

```text
freshness: fresh
status: reconciled
reason: target_not_reached
same_key_status: reconciled
watts: 4.2
hold_active: true
```

Добавлены регрессионные тесты `test_timeout_mismatch_reconciles_as_target_not_reached` и `test_transport_error_mismatch_reconciles_as_target_not_reached`; оба прошли в повторном полном прогоне. В рамках проведённой проверки открытых P1/P2 замечаний после исправлений не осталось. Это не заменяет проверки Android на устройстве.

### P2 — Экран назначения показывал успешное сохранение отвергнутого ввода

В `src/app/setup.tsx` экран проверял только непустое имя. Домен отклоняет имя или помещение длиннее 80 символов, а экран независимо переходил к «Устройство назначено». Основной исполнитель добавил ограничения `maxLength={80}` и проверку длины обоих полей перед `assign`. Исправление подтверждено чтением обновлённого исходника; отдельный Android UI-прогон не выполнен.

### P2 — Возобновление onboarding могло перехватить переход к настройке

Эффект `src/app/index.tsx` реагировал на любое изменение `data.onboarded`. Действие выбора контроллера одновременно вызывало `setOnboarded()` и `router.push('/setup')`; эффект мог заменить верхний экран на `/home`. Основной исполнитель добавил `resumed` ref: возвращение сохранённой сессии выполняется один раз после гидратации. Изменение подтверждено исходником. На Android навигация ещё не проверена.

## Проверенные свойства

- Backend проверяет владельца контроллера на каждом ресурсном маршруте; чужой ресурс скрывается ответом 404.
- Пароли хешируются scrypt; bearer-токены случайные, в SQLite сохраняются их SHA-256 хеши, срок сессии проверяется на запросе.
- CH3 защищён на уровне домена, API и CHECK-ограничения SQLite; назначение картинки не меняет номинальную мощность или защиту.
- API повторно проверяет разрешения, ручной приоритет, свежесть и предел мощности при отправке симулятором.
- Ключ идемпотентности уникален в рамках контроллера, несовпадающий повтор отклоняется. Запрос не меняет показания до явного шага симулятора.
- URL клиента запрещает credentials, query/hash, посторонние пути и произвольный HTTP. HTTP разрешён только явным loopback/emulator адресам в development; редиректы запрещены.
- Нативный bearer-токен хранится в SecureStore, веб-токен — в памяти. Демо не использует этот транспорт и не содержит серверных секретов.
- Мобильный план требует разрешения CH2, включённого автопилота, свежих значений, отсутствия ручного приоритета и допустимого окна. Уже работающая LED-лента не получает новый план запуска.
- Применённое демопредложение сохраняет исходный график и показатели после перезапуска; оно меняет будущую запись расписания, а не изображает подтверждение реле.
- Некорректная сохранённая демотелеметрия CH3 не заменяется вымышленными показаниями: состояние отклоняется целиком.

## Фактическая проверка

Из `mobile/specwatt-app`:

```text
node --experimental-strip-types --test tests/*.test.mjs
13 tests, 13 pass, 0 fail
npx tsc --noEmit
exit 0
```

Из `backend`:

```text
python -m unittest discover -s tests -v
Ran 19 tests in 14.413s — OK
```

Первоначальный backend-прогон (17 тестов) не покрывал несовпадающее завершение `timeout`; проблема была воспроизведена отдельно, исправлена и повторно проверена уже набором из 19 тестов. Во время запуска присутствовали предупреждения Node о typeless package и Starlette об устаревшей интеграции httpx; они не превратились в ошибки тестов.

## Ограничения поставки

Доказательств собранного и запущенного Android APK, проверки TalkBack/Android Back на устройстве или работы Android → FastAPI → ESP32 нет. Сохранённые расписания локального демо не исполняются по часам. Не реализованы восстановление пароля, подтверждение почты, удаление серверного аккаунта, публичная инфраструктура и аппаратный транспорт. Регистрация относится к локальному серверному симулятору. Эти ограничения должны оставаться явными в финальном отчёте и документации.
