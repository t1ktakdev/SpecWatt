# Серверный планировщик нагрузок SpecWATT — устройство и алгоритм

Ветка: `feature/backend-durable-scheduler`. Статус: реализован, 58 тестов зелёные
(19 прежних + 39 новых), smoke-скрипт проходит. Это серверный движок планирования
для существующего FastAPI/SQLite симулятора; аппаратное управление не
затрагивается.

## 1. Что существовало и что добавлено

**Существовало (не переписывалось, только механическая интеграция):**
приложение-фабрика `create_app`, raw SQLite (схема v1), аккаунты/сессии (scrypt +
opaque bearer-токены), конвейер команд с идемпотентностью и одним in-flight
командованием на контроллер, повторные проверки при dispatch (защита, свежесть,
согласие, ручной приоритет, пик), журнал `events`, история `measurements`,
явные шаги симулятора `/simulator/step` и авторитетная телеметрия.

**Добавлено:**

| Модуль | Назначение |
| --- | --- |
| `specwatt_api/clock.py` | `SystemClock` / `VirtualClock` — единая точка времени сервера |
| `specwatt_api/base.py` | общие константы (`CHANNELS`, `FRESH_SECONDS`) и строгая база `Input` (разрывает цикл импортов) |
| `specwatt_api/scheduler/models.py` | контракты API, статусы, константы (горизонт 7 суток, минимальная длительность 1 с) |
| `specwatt_api/scheduler/engine.py` | чистая детерминированная математика планирования (без БД и HTTP) |
| `specwatt_api/scheduler/store.py` | таблица `schedules` (схема v2), CRUD |
| `specwatt_api/scheduler/runner.py` | tick — синхронный проход по активным расписаниям |
| `specwatt_api/scheduler/router.py` | 7 эндпоинтов с той же авторизацией и владением |
| `backend/scripts/scheduler_demo.py` | демонстрация виртуального времени (13:59 → 14:00 → 14:30) |
| `backend/scripts/export_openapi.py` | экспорт OpenAPI без включения публичных `/docs` |

Изменения в `app.py`: инъекция часов (`create_app(db, clock=...)`, все
`time.time()` → `clock.now()`; rate-limit намеренно остался на
`time.monotonic()`), миграция схемы до v2, извлечение общего ядра выдачи команд
`issue_command()` (поведение эндпоинта команд сохранено байт-в-байт, проверено
прежними тестами), подключение маршрутов.

## 2. Модель расписания

Расписание — окно работы устройства:

* `action='on'` — окно `[start_at, end_at]`, `end_at = start_at + duration_seconds`.
  В начале окна выдаётся команда включения, в конце — выключения.
* `action='off'` — одиночное выключение в `start_at` (без длительности).

Состояния: `pending` → `running` → `completed`; терминальные `cancelled`,
`rejected` (с причиной), `uncertain` (неоднозначный результат команды).
Фазы: `start` / `end`; каждое расписание ссылается на текущую команду
(`command_id`).

## 3. Машина состояний tick

Tick не спит и не порождает потоков: `POST .../scheduler/tick` — один
синхронный проход по активным расписаниям в транзакции `BEGIN IMMEDIATE` в
текущее время часов приложения. Пользователь (тест, демонстрация, будущий
операторский цикл) переводит время и вызывает tick явно — каждый dispatch
воспроизводим и аудитирован.

```
pending ──(окно наступило)──▶ running(фаза start, команда включения)
   │                            │
   ├─ rejected: guard/окно      ├─ acknowledged ─▶ фаза end (для 'on')
   │  пропущено                 ├─ timeout/transport-error ─▶ uncertain
   ├─ command_in_flight ─       ├─ rejected: guard ─▶ rejected
   │  отложено до след. tick    └─ reconciled: цель достигнута ─▶ как ack;
   └─ 'off': ack ─▶ completed      цель не достигнута ─▶ rejected

running(фаза end) ──(now ≥ end_at, выдаётся выключение, позднее исполнение
допустимо — отказоустойчивое off)──▶ ack ─▶ completed
```

Ключевые решения:

* **Повторное исполнение невозможно.** Каждая фаза выводит стабильный
  идемпотентный ключ `schedule-{id}-{start|end}`; вставка команды и смена
  статуса расписания происходят в одной транзакции; повторный tick видит уже
  выставленный статус и не выдаёт команду второй раз.
* **Отмена.** `cancel` переводит расписание в `cancelled` в той же транзакции;
  runner читает только `pending/running/uncertain`. Отменённое не исполняется;
  команда, уже находящаяся in-flight, продолжает собственный жизненный цикл
  (отозвать отправленную команду нельзя — это документированное поведение).
* **Неоднозначный результат.** `timeout`/`transport-error` переводят
  расписание в `uncertain`; автоматический повтор запрещён. Разрешение —
  только через существующий поток авторитетной телеметрии: `reconciled` с
  совпадением цели продолжает работу, с `target_not_reached` — терминальный
  `rejected`. Команда не дублируется.
* **Пропущенное окно.** Если сервер был недоступен и окно `on` истекло
  (`now > end_at`), расписание получает `rejected/window_missed` — исполнение
  «задним числом» нарушило бы намерение владельца. Для одиночного `off`
  действует допуск `MAX_LATE_OFF_SECONDS` (3600 с). Закрывающее выключение
  окна `on` выполняется и с опозданием: оставить устройство включённым хуже.
* **Транзиентный отказ.** Причина `command_in_flight` (одно in-flight
  командование на контроллер по контракту ядра) оставляет расписание
  `pending` до следующего tick — это временное состояние по определению.
  Все остальные причины guard'ов — терминальный `rejected` с причиной.

## 4. Guard'ы: три согласованных уровня

Уровни сравнимы по порядку с `command_rejection()` ядра:

1. **Создание/изменение** (`engine.evaluate_plan`): protected → stale →
   automation → manual-priority → окно (прошлое/дальше 7 суток) → конфликт
   расписаний → минимальный уровень нагрузки (2.4 Вт CH3 + номинал устройства)
   → прогнозный пик.
2. **Dispatch** (каждый tick): команды выдаются только через общее ядро
   `issue_command` → `command_rejection()` — тот же guard-путь, что и у
   интерактивных команд, плюс повторные проверки симулятора при `/step`.
3. **Схема БД** (v2): `schedules.channel_id CHECK (IN ('CH1','CH2'))` — CH3
   запрещён в расписаниях даже прямым SQL; статус ограничен перечислением.

Планировщик структурно не имеет обходного пути: единственный способ создать
команду — `issue_command`, где `protected_channel` проверяется первым.

## 5. Прогнозная модель нагрузки (детерминированная)

* Базовая линия: последнее измеренное значение каждого канала держится
  постоянным на всём горизонте (консервативно — постоянную нагрузку не
  занижаем). Для CH3 это всегда 2.4 Вт.
* Активное расписание `on` даёт номинал (`CHANNELS`) в своём окне и возвращает
  базовую линию вне его. Для выключенного сейчас канала это моделирует запуск
  и останов; для включённого — консервативно после окна.
* Значения помечены `basis: measured|forecast` и `source`; merged-сегменты
  суммируются по границам (half-open интервалы, coalescing только при равных
  мощности И basis — переход тега не стирается).
* Метрики: `projected_peak_watts` (+момент), `plan_energy_wh`,
  `baseline_energy_wh`, `delta_energy_wh`, `device_energy_wh`,
  `above_peak_duration_s`, сегменты окна. Энергия = Вт·с / 3600 = Вт·ч;
  интегрируется только по окну плана.
* **Честность энергии:** уменьшение пика не выдаётся за экономию энергии.
  План для уже включённого устройства даёт `delta_energy_wh ≈ 0` при любом
  сдвиге пика; это закреплено тестом `test_energy_honesty_*`.
* **Невыполнимые планы:** `nominal_exceeds_peak` (2.4 Вт CH3 + номинал > лимит)
  — план невозможен никогда, подсказки пусты; `peak_exceeded` — план не
  проходит в запрошенное время, и `find_slots` детерминированно предлагает до
  5 допустимых стартов (запрошенный старт + концы существующих расписаний,
  по возрастанию). Кандидаты, где старт-конфликт или пик не проходят,
  отбрасываются.

## 6. Виртуальное время

`VirtualClock(start)` подставляется в `create_app(..., clock=clock)`. Все
метки времени (сессии, измерения, команды, расписания, журнал) идут через
часы, поэтому:

* «13:59 → 14:00» — это `clock.advance(60)` + обновление телеметрии
  (реальные устройства отчитываются непрерывно; без свежей пробы сервер
  честно считает измерения устаревшими — guard `stale_measurements`);
* перезапуск сервера воспроизводится созданием нового `create_app` на той же
  БД и тех же часах;
* ни один тест не ждёт реального времени; 39 новых тестов выполняются ~14 с.
  Демонстрация: `python scripts/scheduler_demo.py`.

## 7. Ограничения (честный список)

* Фонового цикла нет по дизайну: tick явный. Продакшен-обёртка (поток/задача
  планировщика ОС, вызывающая `run_due_schedules` раз в секунду) — отдельное
  решение, здесь только API и функция.
* Прогноз держит базовую линию постоянной: ручные переключения, произошедшие
  между созданием и исполнением, учитываются только повторными проверками при
  dispatch, а не прогнозом.
* Если измерения устарели к моменту закрывающего выключения, `off` будет
  отклонён (`end_phase_stale_measurements`), устройство останется включённым,
  расписание — `rejected` с причиной; разруливает оператор. Это плата за
  «нет догадок о состоянии» (философия ядра).
* Отмена не отзывает уже отправленную in-flight команду (отозвать отправленное
  нельзя; см. ядро команд).
* Отложенные из-за `command_in_flight` расписания требуют повторных tick'ов;
  один dispatch за проход на контроллер.
* Retention `events`/`measurements` не ограничен (унаследовано от ядра).
* Аппаратная интеграция, реальный ESP32-транспорт, кворум подтверждений — вне
  области этого модуля (см. SECURITY.md ядра).

## 8. Безопасное объединение с основной веткой

1. Ветка основана на текущем `main` (`8a123c8`), правки только в `backend/`
   (`specwatt_api/*`, `tests/*`, `scripts/*`, `docs/*`) — с мобильной частью
   и дизайном конфликтов нет.
2. Перед merge: `git fetch origin && git rebase origin/main` (или merge) и
   полный прогон: `python -m unittest discover -s tests -v` (58 тестов) +
   `python scripts/smoke.py`.
3. Изменения `app.py` ограничены: импорт `base`/`clock`, сигнатуры помощников
   (`now=`), `issue_command`, миграция v2, подключение маршрутов. Если другой
   агент менял те же функции — точка конфликта одна, референс: соответствующие
   тесты `test_api.py` должны остаться зелёными без изменений.
4. Схема: v1 → v2 миграция идемпотентна (`CREATE TABLE IF NOT EXISTS` +
   `PRAGMA user_version=2`); старые БД поднимаются без ручных шагов. Откат
   ветки безопасен: старый код читает v2-БД? Нет — `user_version=2` старый код
   отвергнет («newer than this server»), поэтому откатывать надо вместе с БД
   (backup-политика ядра).
5. Public API: только добавления (новые маршруты), существующие формы ответов
   не менялись; `/docs` и `/openapi.json` остались отключены — контракт фронта
   описан в `docs/openapi.json` и `SCHEDULER_API.md`.
6. Коммиты локальные; push и merge в main — только по отдельному разрешению
   владельца репозитория.
